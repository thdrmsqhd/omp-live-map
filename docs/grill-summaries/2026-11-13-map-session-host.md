## Grill Summary (with-docs)

기준 문서: `README.md`, `AGENTS.md`, `server/prompt.js`, `server/tail.js`, `server.js`, omp v18.20.0 내장 문서(`rpc.md`, `approval-mode.md`, `tools/ask.md`, `tools/task.md`).

### Intent
- Problem: 맵 하나만으로 업무를 진행하고 싶다. 지금은 세션을 열려면 omp TUI가 필요하고, 맵은 기존 세션에 `omp -p -r`로 프롬프트만 보낸다.
- "omp 없어도"의 뜻: omp TUI를 띄우지 않는다. 실행 엔진은 omp 바이너리를 headless로 계속 쓴다.
- Success criterion: 터미널 UI 없이 맵에서 새 세션을 열고 대화를 시작한다. 서브에이전트가 하는 일을 글자 단위로 실시간으로 본다.
- Scope: 계획 필요(ADR 작성).

### Contract
- Inputs: 브라우저(로컬 사용자 1명) → 맵 서버. 새 세션은 작업 폴더(cwd)와 첫 프롬프트. 모델·승인 방식·비용 상한은 받지 않고 omp 설정을 따른다.
- Outputs: 새 세션 카드, 본 세션과 서브에이전트의 글자 단위 스트리밍, 툴 호출 표시, `ask` 대화상자.
- Invariants:
  - 세션 하나를 동시에 돌리는 omp 프로세스는 1개다.
  - 세션 기록(jsonl)은 omp만 쓴다. 맵 서버는 읽기만 한다.
  - 의존성 0, `127.0.0.1` 바인드, 파일당 200줄 미만.
  - 맵에서 만든 세션을 세션 종료(stop) 뒤 omp TUI로 이어 쓸 수 있다.
- 불변 조건으로 고르지 않은 것: 서버 재시작 뒤 실행 유지, 자동 승인 금지.

### Decisions
- ADR-0001: 맵 세션은 세션마다 상주하는 `omp --mode rpc-ui` 프로세스로 실행한다 (`docs/adr/0001-map-session-per-rpc-process.md`)
- ADR-0002: 스냅샷의 원본은 jsonl 하나이고, 맵 서버는 자기 상태를 저장하지 않는다 (`docs/adr/0002-jsonl-single-source-no-server-state.md`)
- ADR로 남기지 않은 결정(쉽게 바꿀 수 있음):
  - TUI 세션 카드는 읽기 전용, "TUI 사용 중" 표시.
  - 서브에이전트 구독은 항상 `events`.
  - 맵이 강제하는 상한 없음.
  - 이름: 맵 세션 / TUI 세션 / 빈 세션, 세션 종료(stop). 기존 "세션 프로세스 종료"는 "프로세스 정리"로 바꾼다.

### Accepted risks
- `tools.approvalMode = yolo`, `ask.timeout = 0`, 상한 없음. 턴은 확인 없이 파일 쓰기·명령 실행을 하며 사용자가 멈출 때까지 진행한다.
- 맵 세션마다 omp 프로세스가 상주한다(본체 122~575MB, 자식 평균 100MB. RAM 16GB 중 여유 4.8GB).
- 맵 서버가 내려가면 맵 세션 전부가 턴 도중에 끊긴다. 자동 복구는 없다.
- 서브에이전트 `events` 프레임은 전체 메시지를 매번 담아 stdout 양이 크다.

### Open threads
- "중단됨" 판정: 서버가 맵 세션 목록을 저장하지 않으므로 기록 파일만으로 끊긴 턴을 가려야 한다. jsonl에 그 표시가 남는지 확인하지 않았다.
- TUI가 잡은 세션에 `omp --mode rpc-ui -r <파일>`을 붙이면 omp가 거부하는지 확인하지 않았다. 거부하지 않으면 맵이 띄우기 직전에 `omp session lease`를 조회해야 하고, 조회와 기동 사이의 틈이 남는다.
- rpc 프로토콜 v1에 머물지 v2(`rpc_chunk` 재조립)를 구현할지. v1은 큰 프레임의 문자열을 잘라 보내는데, 원본이 jsonl이라 임시 표시에는 영향이 작다.
- `--mode rpc`에서도 `extension_ui_request`가 나왔다(2026-11-13 확인). 맵이 모르는 요청을 어떻게 답할지 정해야 한다.
- `ask` 대화상자와 채팅에 그리는 글자는 에이전트가 만든 내용이다. 셸 실행 API가 있는 서버라서 화면에 넣을 때 전부 `esc()`를 거쳐야 한다.
- 새 세션을 여는 화면 위치(빈 바탕 메뉴, 로컬 작업 카드에서 전환)와 수동 전달 버튼 위치.
- 구현 뒤 README 수정: "채팅 Ctrl+Enter" 행, `/api/prompt`의 `busy` 설명, 세션·프로세스 귀속 문단, 검증 항목의 가짜 `omp.exe` 방법.

### Recommendation
- ready for writing-plans. 계획 첫 단계로 위 미확인 2개("중단됨" 판정, TUI 세션에 `-r` 기동 시 동작)를 실험으로 확인한다.

## 2차 정리 (같은 날, 관점 재확인)

요약과 시각화를 본 뒤 사용자가 관점을 다시 말했고, 질문 5개를 더 거쳐 아래로 정리했다. 1차 결정(ADR-0001, ADR-0002)은 그대로 유지한다.

### Intent (최종)
- 입력 원문: "웹에서 새로운 세션을 열고 파일을 첨부하고 그냥 LLM Agent를 쓰는 느낌". 터미널 화면(TUI)은 쓰지 않는다.
- Success criterion: 하루 업무 동안 터미널 화면을 한 번도 열지 않는다.
- 기준으로 삼은 제품: Claude Code 데스크톱·웹. 기능 전체를 똑같이 갖추는 것은 끝을 정할 수 없어 완료 기준으로 쓰지 않고, 아래 14개 목록으로 대신한다.

### Scope (사용자가 고른 14개. 5개와 9개로 나눈 것은 제안이며 확정 전)
- 먼저 만들 5개: 새 세션 열기·지난 세션 이어가기 / 파일·이미지 첨부 / 지시·도는 중 추가 지시·멈추기 / 에이전트 질문에 답하기 / 서브에이전트가 하는 일 실시간 보기.
- 그다음 9개(순서 미정): 모델·생각 깊이 변경 / 명령·스킬 실행 / 서브에이전트 개별 멈춤·지시 / 대화 압축·인계 문서 / 바뀐 파일 내용 보기 / 대화 되돌리기·갈라 진행 / 목표 모드 / 작업 단계 한눈에 보기 / 비용·시간 기준 초과 시 알림 또는 멈춤.
- 하지 않는 4개: TUI 세션 조종(보기만) / 맵이 직접 LLM 호출 / 세션 간 자동 흐름 / 클라우드·원격·휴대폰.

### 버린 방향
- TUI는 두고 맵이 밖에서 감독·조종하는 구조(omp Collab, 로컬 relay). 사용자가 TUI를 쓰지 않으므로 필요 없다. 이 방향의 질문 2개와 답은 무효로 한다.
- Claude Code 데스크톱 기능 전체 동등.

### Open threads (추가)
- 서로 다른 답: 1차 질문 7에서는 "상한 없음", 2차에서는 "비용·시간 기준 초과 시 알림 또는 멈춤"을 골랐다. 알림만 할지, 멈출지, 기준 금액을 정해야 한다. 정해지면 ADR-0001의 상한 문장을 고친다.
- 첨부 파일 전달 방법. rpc `prompt`는 이미지를 그대로 받는다. 다른 파일은 브라우저가 내용만 넘기므로 맵 서버가 임시 폴더에 저장한 뒤 경로를 넘겨야 한다. ADR-0002의 "맵 서버는 디스크에 아무것도 쓰지 않는다"에 예외가 생긴다.
- 의존성 0·파일당 200줄 규칙과 파일 편집기·대화형 터미널·변경 검토 화면의 충돌. 사용자가 답하지 않았다. 답이 나올 때까지 규칙을 유지한다.
- 나중 9개의 순서.

### Recommendation
- ready for writing-plans. 계획 범위는 "먼저 만들 5개"로 잡는다. 사용자가 5개/9개 구분을 확정해야 한다.
- grill은 여기서 끝낸다. 사용자가 용어가 많은 질문에 "모르겠다"고 두 번 답했다.

## 3차 정리 (같은 날, 중심 교정)

2차 정리는 "터미널 화면을 쓰지 않는다"에 무게를 뒀는데, 사용자가 그것이 요점이 아니라고 바로잡았다. ADR-0001, ADR-0002는 그대로 유지한다.

### Intent (최종)
- 입력 원문: "맵안에서 여러개의 에이전트 여러개의 세션 그리고 각 세션의 파일트리, 리소스, 사용 금액, 서브에이전트, 백그라운드잡 등등 업무 OS로서 내가 관제한다".
- 맵은 업무 OS다. 세션 여러 개와 에이전트 여러 개를 한 화면에서 보고 사용자가 직접 조종한다. 터미널을 쓰지 않게 되는 것은 결과이지 목표가 아니다.
- Success criterion(제안, 확정 전): 세션 3개 이상을 맵에서 열어 동시에 돌리고, 세션마다 파일 트리·자원·사용 금액·서브에이전트·백그라운드 잡을 보면서, 맵에서 지시·멈춤·질문 응답·세션 종료를 한다.

### 관제 대상 7종 대조 (README, `server/snapshot.js`, `ui/js/view/menu.js`, `ui/index.html` 기준)
- 보기는 7종 모두 지금 맵에 있다: 세션, 에이전트·서브에이전트, 파일 트리, 자원, 사용 금액, 백그라운드 잡, WSL·Docker.
- 지금 되는 조종 7개: 기존 세션에 지시 전송 / 전송 취소 / 세션에 딸린 프로세스 정리 / 잡 시작 / 잡 중지 / 셸 명령 실행 / WSL·Docker 시작·중지·재시작.
- 빠진 조종 7개: 새 세션 열기 / 세션 종료 / 도는 중 추가 지시 / 파일 첨부 / 되묻는 질문에 답하기 / 서브에이전트 개별 멈춤·지시 / 금액·시간 기준 초과 시 알림 또는 멈춤.
- 빠진 보기 3개: 서브에이전트 글 실시간 / 전체 합계 줄(세션 수·에이전트 수·오늘 비용·RAM. 상단 바에는 거르기·검색·확대만 있다) / 에이전트가 건드린 파일 표시(스냅샷 `files`에 모으지만 UI에서 쓰지 않는다).

### 만드는 순서 제안 (확정 전)
1. 맵에서 세션 열고 끄기: 새 세션, 세션 종료, 지시·추가 지시·멈춤, 파일 첨부.
2. 되묻는 질문에 답하기, 답을 기다리는 세션 표시.
3. 서브에이전트 관제: 글 실시간, 개별 멈춤·지시.
4. 전체 합계 줄.
5. 금액 기준 알림·멈춤, 에이전트가 건드린 파일 표시.

2차에서 고른 14개 중 위 순서에 없는 6개(모델·생각 깊이 변경, 명령·스킬 실행, 대화 압축·인계, 대화 되돌리기·갈라 진행, 목표 모드, 작업 단계 한눈에 보기)는 그 뒤로 둔다.

### Open threads (3차 기준)
- 금액 기준: "제한 없음"과 "초과 시 알림 또는 멈춤"이 갈려 있다.
- 첨부 파일 전달 방법(ADR-0002 예외 여부).
- "등등"에 더 들어갈 관제 대상.

### Recommendation
- ready for writing-plans. 사용자가 완료 기준과 순서를 확정하면 1번부터 계획을 세운다.

## 4차 정리 (같은 날, 깊이와 실시간)

3차 정리를 그리는 도중 사용자가 세 가지를 더했다. 3차의 "보기는 7종 모두 이미 있다"는 대상이 화면에 있다는 뜻일 뿐, 요구한 깊이와 속도에는 못 미친다.

### Intent (최종)
- 입력 원문: "잡이 뭘하고 있는지 서브에이전트가 뭘 어떻게 하고 있는지 완전 마이크로 매니징 관점으로 봐야해" · "실시간 이게 주요점이야" · "서브에이전트도 각각의 세션이랑 동등한 레벨로 카드가 관리되어야" · "잡도 자기가 실행중이면 뭔가 응답도 스트리밍 되어야지".
- 맵은 업무 OS다. 세션·서브에이전트·잡을 같은 급의 카드로 다루고, 각 카드가 지금 무엇을 어떻게 하는지 실시간으로, 툴 호출 하나와 출력 한 줄까지 보면서 조종한다.
- 요점은 실시간이다.

### 원칙 (용어집에 반영)
- 카드 하나는 일하는 주체 하나다. 메인 에이전트, 서브에이전트, 잡이 같은 틀(지금 하는 일이 실시간으로 흐르는 칸, 멈춤, 지시)을 쓴다.

### 지금 보이는 깊이와 지연 (코드 대조)
- 글: 메시지가 끝난 뒤, 앞 700자(`turns.js`). 맵에서 보낸 지시의 메인 답변만 글자 단위(`prompt.js`).
- 생각: 읽지 않는다. 기록에는 있다(이 세션 jsonl에 `thinking` 47개).
- 툴 호출: 이름과 횟수, 마지막 의도만(`ingest.js`). 기록의 `tool_execution_start`에는 시작 시각과 인자가 있다. 화면에는 fs.watch 300ms 또는 2초 주기 뒤에 반영된다(`server.js`).
- 툴 결과: 실패 횟수와 잡 감지에만 쓴다. 내용은 버린다.
- 명령: 최근 8개, 앞 140자. 출력 없음.
- 에이전트가 띄운 잡: 잡 번호, 명령(앞 300자), 실행 중·종료, 시각. 출력 없음. 세션 폴더에 출력 파일이 없어 읽을 곳을 찾지 못했다.
- 맵에서 띄운 잡: 1.2초마다 최근 80줄(`app.js`).
- 자원 4초 주기, 금액은 메시지가 끝날 때.

### 서브에이전트·잡의 급
- 서브에이전트 카드는 지금도 메인과 같은 블록으로 열린다(`layout.js`의 `agentKind`가 main·sub를 같이 다룬다). 없는 것은 실시간 흐름, 개별 멈춤, 직접 지시다. 자원은 세션 합계만 잰다(`proc.js`).
- 에이전트가 띄운 잡은 작은 카드뿐이다. 맵에서 띄운 잡은 세션 카드의 `bg` 블록 안에 있다.

### 만드는 순서 제안 (확정 전. 3차의 순서를 대체)
1. 맵이 세션을 직접 띄운다: 새 세션, 종료, 지시, 멈춤.
2. 실시간 흐름: 메인과 서브에이전트의 글·생각·툴 호출·결과.
3. 서브에이전트 카드: 개별 멈춤, 직접 지시.
4. 잡 카드: 출력 스트리밍, 중지.
5. 질문에 답하기, 파일 첨부.
6. 전체 합계 줄, 금액 기준.

### Open threads (4차 기준)
- 에이전트가 띄운 잡의 실시간 출력을 읽을 수 있는가. 계획 첫 실험으로 둔다.
- 글자 단위 실시간과 조종은 맵이 띄운 세션에서만 완전하다. TUI에서 띄운 세션은 기록 tail의 지연(툴 호출 0.3~2초, 글은 메시지 끝)을 그대로 갖는다. 사용자가 이 차이를 받아들이는지 확인하지 않았다.
- 서브에이전트별 자원 분리 가능 여부.
- 툴 결과 전체를 서버 메모리에 둘지, 카드를 열 때 기록에서 읽을지. README의 "서버는 상태를 메모리에만 둔다"와 메모리 사용량에 걸린다.
- 금액 기준("제한 없음" 대 "초과 시 알림 또는 멈춤"), 첨부 파일 전달 방법은 그대로 남아 있다.

### Recommendation
- ready for writing-plans. 순서 1·2가 ADR-0001의 구현 범위다.

## 조사 결과: 에이전트가 띄운 잡의 출력 (2026-11-13)

- 실행 중인 `bg_N` 잡의 출력은 디스크에 남지 않는다. omp 세션 프로세스의 메모리에만 있다(`omp://bash-tool-runtime.md:271-273`, `omp://blob-artifact-architecture.md:17-24`). 세션 jsonl에도 중간 출력은 없다.
- 읽는 길은 하나다. `omp --mode rpc`를 직접 띄운 쪽이 이벤트(`tool_execution_update`)로 받는다(`omp://rpc.md:887`, `omp://tools/bash.md:89-91`). 이벤트 안의 필드는 문서에 없어 실험으로 확인해야 한다.
- 결론: 잡 출력 스트리밍은 맵이 직접 띄운 세션에서만 된다. TUI에서 띄운 세션의 잡은 명령과 상태까지만 보인다. ADR-0001(맵이 세션마다 rpc 프로세스를 소유)의 근거가 하나 늘었다.
- 이름을 붙여 띄운 서비스(`omp ps`에 뜨는 것)는 디스크 로그가 있어 밖에서 읽을 수 있다(`~/.omp/run/daemons/.../output.log`).

## 결정 추가: 카드에 모델과 단가 표시 (2026-11-13)

- 모든 카드(메인 에이전트, 서브에이전트)에 모델 이름과 단가를 표시한다. 비싼 모델이 직접 일하고 있는 카드는 눈에 띄게 표시한다.
- 목적: 비싼 모델은 판단만 하고 실제 작업은 싸고 빠른 모델이 하는지를 관제한다.
- 정할 것: 단가를 어디서 가져올지(omp 모델 설정 또는 기록의 메시지별 비용), "비싼 모델"의 기준, "직접 일한다"의 판정(툴 호출을 직접 하는지).
- 만드는 순서에서는 2번(실시간 흐름)과 함께 넣는다.
