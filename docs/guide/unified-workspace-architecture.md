# 통합 관제 워크스페이스: UI 아키텍처 설계안

대상: `omp-live-map` · 이전 작업 세션 `E1nPCOXuUmzp8m3l`의 연속 작업

## 실제 OMP Live Map V3 적용

설치 앱의 **Workflow 관제**에서 실제 실행 상태와 승인·반려를 편집 노드 안에 표시한다. 기존 ASK는 같은 화면의 **개입 필요**에서 답한다. 아래에는 실제 로그·산출물, 오른쪽에는 등록 프로젝트 문서가 표시된다. 편집과 실행 버전이 다르면 같은 페이지에 실행 스냅샷을 표시한다.

6대 계열·18종 유형은 실제 하네스 정의로 저장된다. 연결의 핸드오프 스키마는 보내는 산출물 이름·고정 결과 파일과 맞을 때만 저장된다. 결제·동의·비밀번호·UAC는 지정한 승인 단계에서 다음 작업을 멈추고, 사용자는 원래 창에서 직접 처리한다. 독립 평가는 완료된 실행의 기록된 JSON 산출물만 읽고 실행 기록은 바꾸지 않는다. 외부 브라우저·OS 동작을 가로채거나, 관리형 OMP가 질문을 앱으로 넘기는 경로는 아직 없다. 세션 지도는 유지한다.

| 변경 전 | 변경 후 |
|---|---|
| `설계 · 노드 캔버스` | `Workflow 관제` |
| `setMapMode("map");` 이후 `openMapWorkflowLaunch(picker.value, id)` | 화면을 전환하지 않고 `openMapWorkflowLaunch(picker.value, id)` 호출 |

### 아래 내용은 최초 시제품 설계 기록

## 1. 목표와 적용 범위

설계 중에는 관제로, 실행 중에는 편집 화면으로 이동해야 했던 흐름을 없앤다. 하나의 화면에서 설계 카드, 실행 경로, 개입 요청, 작업 결과, 프로젝트 문서를 함께 본다. 이번 구현은 기존 Live Map과 노드 설계를 덮어쓰지 않는 **로컬 인터랙티브 프로토타입**이다. 기존 두 화면에 프로토타입 진입 링크를 넣었으며 기존 실행 경로, API, 저장소는 변경하지 않았다.

| 영역 | 구현된 상호작용 | 운영판으로 전환할 때 |
|---|---|---|
| 통합 화면 | 같은 캔버스에서 설계 편집과 실행 상태 표시. 상단 개입 버튼으로 대상 카드 이동 | 실제 실행과 설계 버전 매핑, UI의 Live Map/설계 전환을 이 화면으로 대체 |
| 독립 엔티티 카드 | Workflow·프로필·루프·하네스 추가/편집/삭제. Workflow 카드에서 프로필·루프를 지정하고 작업 지시를 선택 | Workflow별 그래프와 프로필/루프 버전 참조 저장, 실행기가 정책을 해석 |
| 대형 실행 카드 | 입력·출력·스키마·판단 기준·핸드오프·중단 조건의 계층적 표시. 계약선과 상태 배지 | 실제 산출물 미리보기, 큰 그래프에서 다중 선택·가상화·위치 배치 |
| 작업 수행 내역 | 페이지 폭을 사용하는 작업 지시, 타임라인, 산출물/개입 필터, 관련 노드 이동. 내부 로그 스크롤 없음 | 서버 이벤트 및 아티팩트 링크, 장기 실행 로그 페이지네이션 |
| ASK / HITL | 인라인 답변·수정·승인·반려. 민감 승인 관문은 수정만으로 통과하지 않음 | 실행기가 의무 관문을 강제. 감사 로그와 권한·만료·중복 검증 |
| 프로젝트 문서 | 목적·진행·결정 요약, 출처와 원문, 명시적으로 고른 MD/TXT. 브라우저 파일 핸들이 있는 경우 4초마다 변경 재확인 | 프로젝트에 허용된 문서 인덱스, 변경 이벤트, 문단 단위 출처 및 캐시 |

현재 화면은 한 개의 작업 그래프를 편집한다. 여러 Workflow 카드를 추가해 작업 지시와 연결 정책을 바꿀 수 있지만 Workflow마다 별도 그래프를 저장하거나 실행하지는 않는다. 루프 정책과 프로필은 편집 가능한 설계 데이터다. 스케줄링, 봉인 평가, 어댑터 호출, 실제 재시도·권한 승인·배포는 수행하지 않는다.

## 2. 화면과 인터랙션

1. **상단 명령 바:** 설계 저장, 모의 실행, 완료 단계 수, 미처리 개입과 수행 내역 바로가기. 설계 변경은 다음 실행에만 반영되고 현재 실행의 스냅샷은 고정한다.
2. **중앙 캔버스:** Workflow·프로필·루프 구성 카드, 하네스 실행 카드, 파생 상태 배지, 핸드오프 연결. 확장 카드에는 `입력 → 출력 / 판단 기준 / 핸드오프 / 중단 조건`을 모두 표시한다. 카드의 편집 버튼으로 같은 화면 위에 슬라이드오버를 연다. 일반 경로는 실선, 외부 평가는 점선으로 구분한다. 운영판에서는 카드의 공간 배치와 실행 순서를 별도로 저장한다.
3. **인라인 개입:** 활성 카드와 상단에 동시 표시. ASK는 응답 또는 승인으로 이어가고, 반려는 후속 실행을 중단한다. 수정 지시는 기록에 남긴다. 민감한 HITL은 수정 후에도 대기하며 비밀번호, 결제 정보, OS 승인을 이 UI로 받지 않는다.
4. **수행 내역:** 메인 열 전체에 작업 지시 원문과 타임라인을 배치한다. 산출물에는 받은 계약, 출력 스키마, 모의 결과를 적고 관련 카드를 연결한다. 오류·대기 상태는 색과 텍스트 모두로 구분한다.
5. **오른쪽 컨텍스트:** 목적·진행 현황·주요 결정을 문서 제목/절과 함께 표시한다. 제목은 원문 보기로 연결한다. 파일 핸들을 지원하지 않는 환경에서는 파일 입력으로 선택하고 재선택 시 갱신한다. 파일은 탭 종료 후 다시 연결해야 한다. 모바일에서는 캔버스 다음에 컨텍스트와 수행 내역을 세로로 배치한다.

## 3. 데이터 모델과 실행 경계

| 객체 | 필드와 계약 |
|---|---|
| `HarnessType` | `id`, `family`, `label`, `input`, `output`, `outputSchema`, `criteria`, `handoff`, `stop`. 판단 기준이 달라지면 유형을 분리하고, 입력만 다르면 같은 유형의 설정을 변경한다. |
| `Design` | `version`, `workflowId`, `nodes[]`, `edges[]`. `Node`: `id`, `kind`, `name`; 하네스에는 `type`, `inputSchema` 및 계약 설명을 추가. Workflow에는 `value`, `profileId`, `loopId`; 루프에는 `limit`. |
| `Edge` | `from`, `to`, `schema`. 프로토타입은 송신 `outputSchema` = `schema` = 수신 `inputSchema` 일치 여부와 중복·자기 연결·순환을 검사한다. 여러 입력의 실제 JSON 구조 검증과 스키마 버전은 운영 어댑터의 책임이다. |
| `Run` | `id`, 설계 `snapshot`, 지시 원문, 노드 순서, 상태, 결과, 로그, 대기 요청. 자체 시계와 샘플 데이터만 사용한다. 실행/질문 답변/문서 내용은 디스크에 저장하지 않는다. 설계만 사용자의 저장 동작으로 `localStorage`에 기록한다. |
| `DocNote` | 파일 식별자, 이름, 유형, 절 제목, 짧은 원문 인용. 휴리스틱으로 첫 일치 문장을 추출하며, 못 찾으면 명시한다. 문서 내용은 명령으로 처리하지 않으며 HTML을 렌더링하지 않는다. |

### 외부 평가

평가 하네스는 별도 레인에 배치하고 관찰 연결로만 산출물을 받는다. 평가 노드에서 실행 레인으로 연결할 수 없고, 입력 연결이 없으면 실행하지 않는다. 모의 실행은 목표 품질 점수를 만들지 않는다. 운영판에서는 평가 작업의 실행기, 권한, 문항셋 접근을 대상 실행과 분리한다. 대상 작업에는 문항셋을 전달하지 않으며 평가 결과는 별도 저장소와 지표로 보존한다. 평가 오류가 대상 출력이나 이미 실행한 단계의 상태를 수정해서는 안 된다.

### 실행과 개입 상태

`준비 → 실행 중 → 완료`가 기본이다. 의무 관문/ASK에서는 `실행 중 → 개입 대기`; 승인/ASK 답변은 이어서 진행하고 반려는 `중단`으로 끝낸다. 결제·약관 동의·비밀번호, UAC, 원격 공개는 모의 승인만 허용하며 실제 부작용을 만들지 않는다. ASK 입력, 수정 지시는 현재 탭의 로그에만 표시한다.

### 운영 연동 설계 (이번에 미연결)

- **조회 어댑터:** 기존 Engineering 정의와 Live Map 실행 정보를 공통 ViewModel로 변환한다. 워크플로우 ID·버전 및 노드 ID로 상태를 합친다. 실시간 전송은 이벤트 순번·중복 제거·재접속 커서를 둔다.
- **실행 명령:** 서버가 Workflow 버전·권한·핸드오프 계약을 다시 검증한다. 개입 요청에는 `requestId`, `runId`, `nodeId`, `kind`, `expiresAt`와 허용 응답을 포함한다. 서버에서 유효 상태와 일회성 토큰, 변경 전후 상태, 요청한 사용자, 처리 시간을 기록한다. 같은 요청은 한 번만 처리한다.
- **문서 어댑터:** 선택된 프로젝트의 허용 목록에서만 상대 경로를 해석한다. 화면에는 파일 변경 시각, 개별 출처와 경로를 표시하고, 관련 파일이 이동·삭제된 경우 캐시만 남은 상태를 별도로 표기한다. 문서 본문 및 개인키·토큰 등의 비밀은 외부 호출에 포함하지 않는다.
- **독립 평가 어댑터:** 출력을 불변 아티팩트 ID로 읽는다. 점수, 기준 버전, 회귀 보고서는 평가 작업만 쓴다. 업무 승인과 평가 판단의 상태는 분리한다.

## 4. 6대 계열과 18종

| 계열 | 카탈로그에 구현된 유형 |
|---|---|
| 정보 (4) | 검색, 답변, 요약·추출, 분류·정형화 |
| 생성 (4) | 시각화, 문서, 코드, UI·디자인 |
| 행동 (3) | 브라우저·데스크톱 조작, 시스템 운영, 배포·커밋 |
| 시간 (2) | 예약·알림, 감시 |
| 판단 (3) | 평가, 비교·추천, 진단 |
| 대화 (2) | 인터뷰·코칭, 학습 |

각 유형의 원본 계약과 스키마 키는 `server/engineering/harness-kinds.js`에 선언했다. 예: 검색은 `evidence_list`를 넘기고 답변을 생성하지 않는다. 답변은 `cited_answer`를 생성하고 출처 문제를 검색에 되돌린다. 이 되돌림은 별도 정책이며 스스로 순환하는 실행 Edge를 만들지 않는다.

## 5. 구현 현황

이 문서의 설계는 `index.html`의 설계 모드(`ui/js/design-mode.js`, `ui/js/studio*.js`)와 서버 `server/engineering/harness-kinds.js`에 반영되었다. 설계 단계에서 쓰던 독립 프로토타입(`workspace-prototype.html`)과 그 검증 스크립트는 앱에서 연결이 없어져 2026-11-27에 삭제했다(git 기록에 남아 있다).
